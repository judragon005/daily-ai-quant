## 1. 決策背景與目標

系統每日盤後自動執行。系統篩選 20 檔可投資標的。標的評分介於 0 至 100 分。標的風報比大於等於 2.0。模型審查並剔除高風險標的。系統運作維持 100% 免費。系統防止 GitHub Actions 帳號停權。系統維持極簡架構。

---

## 2. 核心架構決策項目

### 2.1 執行環境決策
- **問題**：系統應在本機執行或雲端執行？
- **論證**：本機執行需要電腦常開。本機網路容易中斷。
- **決策**：**採用 GitHub Actions 雲端排程**。系統無需開啟個人電腦。系統完全免費。

### 2.2 股票母池與初篩標準
- **問題**：全市場掃描耗費時間。API 容易觸發限流。
- **論證**：機構投資重視流動性。低成交量股票存在流動性風險。
- **決策**：**採用分層指數與流動性門檻**。
  - 美股母池：標普 500 與那斯達克 100。
  - 台股母池：臺灣 50 與中型 100。日均成交額大於 5000 萬元。
  - 資料下載時間控制在 60 秒以內。

### 2.3 雙軌評分與交叉驗證
- **問題**：純量化與 AI 模型如何協同運作？
- **論證**：量化計算速度快。AI 模型能辨識財務風險。
- **決策**：**採用雙軌交叉驗證**。
  - 第一軌：計算多因子評分與 2 倍 ATR 風報比。
  - 第二軌：使用 Gemini 審查財務健康度。
  - 否決機制：若標的出現財務舞弊風險，系統立即剔除。

### 2.4 交付管道設計
- **決策**：**採用雙管道交付**。
  - GitHub Pages 部署靜態儀表板網頁。
  - Telegram Bot 於每日 08:00 前發布晨報摘要。

### 2.5 API 金鑰管理
- **問題**：Gemini 免費方案具備每分鐘 15 次呼叫限制。
- **決策**：**建立 API 金鑰輪詢機制**。系統自環境變數讀取多組金鑰。系統輪流使用金鑰。若遭遇 429 錯誤，系統自動切換金鑰。

### 2.6 GitHub Actions 帳號防護措施
- **決策**：落實防護措施，避免服務帳號遭到停權。
  1. 僅允許定時排程與手動觸發。禁止推送觸發。
  2. Commit 訊息一律加上 `[skip ci]` 標籤。避免無限遞迴執行。
  3. 避開整點尖峰時段。台股排定 16:17 執行。美股排定 05:23 執行。
  4. 單次執行時間小於 4 分鐘。

### 2.7 專案結構與防過度工程化
- **決策**：排除複雜設計。
  1. **資料還原**：使用 `auto_adjust=True` 參數。避免除權息跳空誤差。
  2. **休市判斷**：無新交易資料時，系統回傳代碼 0 並直接結束。
  3. **大盤指標**：指數低於 60 日均線時，系統發出防守警報。
  4. **長度限制**：Telegram 訊息長度限制於 3500 字元以內。
